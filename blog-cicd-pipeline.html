Cutting deploy time by 80% with Jenkins and Docker

2026-01-22 · 5 min read

When I joined, deploys were a manual, multi-step process: SSH into a box, pull the latest code, restart services, and hope nothing broke. It worked, but it was slow, error-prone, and entirely dependent on whoever was on call knowing the exact sequence of steps. Redesigning this pipeline cut our release overhead by roughly 80% and made daily releases routine instead of risky.

Containerize first

The single highest-leverage change was moving the application into Docker. Once the app and its dependencies were packaged into an image, "deploying" stopped meaning "configure a server" and started meaning "run this image." Environment drift — the classic "works on staging, breaks on prod" problem — mostly disappeared. 

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

Let Jenkins own the boring parts

With a Jenkins pipeline, every push to main triggers a build, runs tests, builds the Docker image, pushes it to the registry, and deploys it. The pipeline stages map directly to the steps a human used to do manually — the difference is they now run identically every time, in minutes, with full logs. 

pipeline {
  agent any
  stages {
    stage('Build')   { steps { sh 'docker build -t app:${BUILD_NUMBER} .' } }
    stage('Test')    { steps { sh 'docker run app:${BUILD_NUMBER} npm test' } }
    stage('Push')    { steps { sh 'docker push registry/app:${BUILD_NUMBER}' } }
    stage('Deploy')  { steps { sh './deploy.sh ${BUILD_NUMBER}' } }
  }
}

Zero-downtime with rolling deploys

The deploy script doesn't kill the old container before the new one is healthy. It starts the new version, waits for a health check to pass, switches traffic over, and only then retires the old container. This single change removed the brief outage window that used to accompany every release.

What this unlocked

Beyond the raw time savings, the bigger shift was psychological — releases stopped being scary events scheduled around "safe" windows and became routine. That's what let us move to daily releases, and it freed up the time previously spent on manual deploy babysitting for actual engineering work like Auto Scaling tuning and dashboard improvements that further cut our mean time to detect by ~40%.
